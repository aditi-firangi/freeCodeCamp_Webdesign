Introduction

A REST API is an interface that allows applications to communicate with each other over HTTP. REST stands for Representational State Transfer.

Instead of directly accessing another application's internal database, a client communicates with resources exposed through defined API endpoints.

A REST API commonly represents information using JSON. For example, a server might return a customer as a JSON object containing an identifier, name, and email address.

A typical REST endpoint can look like GET /api/customers.

REST APIs are commonly used by web applications, mobile applications, desktop software, and services that need to exchange data.

Example resource

GET /api/products
  • Clients send HTTP requests to API endpoints.
  • The server processes the request.
  • The server returns a response.
HTTP Methods

HTTP methods describe the operation that a client wants the server to perform.

The most commonly used methods in REST APIs are GET, POST, PUT, PATCH, and DELETE.

GET is normally used to retrieve information without changing the resource.

GET /api/products/25

POST is generally used when creating a new resource.

POST /api/products

PUT can be used when replacing an existing resource, while PATCH is useful when only selected properties need to be changed.

PATCH /api/products/25

DELETE requests are used to remove a resource.

DELETE /api/products/25
  • GET retrieves a resource.
  • POST creates a resource.
  • PUT replaces a resource.
  • PATCH partially updates a resource.
  • DELETE removes a resource.
Request and Response

Every API interaction consists of a request from the client and a response from the server.

A request can contain a URL, HTTP method, headers, query parameters, and a request body.

Query parameters are useful when a client needs to filter, sort, or paginate a collection.

GET /api/products?category=books

A request body is commonly used with POST, PUT, and PATCH requests to send data to the server.

{ "name": "Wireless Keyboard", "price": 49.99 }

The response normally contains a status code, response headers, and optionally a response body.

Content-Type: application/json
  • Requests originate from a client.
  • Headers provide additional request information.
  • Query parameters can refine a request.
  • The response contains an HTTP status code.
  • JSON is frequently used as the response format.
Authentication

APIs often need to determine whether a client is allowed to access a particular resource.

Authentication verifies the identity of the client or user making the request.

One common approach is to use a bearer token in the Authorization header.

Authorization: Bearer YOUR_ACCESS_TOKEN

The server validates the supplied credentials before processing protected operations.

API keys are another mechanism that can be used to identify an application or client.

X-API-Key: YOUR_API_KEY

Sensitive credentials should never be embedded directly into client-side source code or committed to a public source-code repository.

  • Protect private API credentials.
  • Use HTTPS when transmitting sensitive information.
  • Give credentials only the permissions they require.
  • Rotate credentials when necessary.
Error Handling

A well-designed API should provide useful information when a request cannot be completed successfully.

HTTP status codes allow clients to understand the general result of a request.

A successful request might return status code 200 OK.

When a new resource has been created, the server can return 201 Created.

Invalid input is commonly represented using a 400 Bad Request response.

If authentication is missing or invalid, the server can return 401 Unauthorized.

A request for a resource that does not exist can return 404 Not Found.

{ "error": "Product was not found" }
  • Use appropriate HTTP status codes.
  • Return useful error information.
  • Avoid exposing internal server details.
  • Keep error responses consistent.
Best Practices

Consistent API design makes an application easier to understand, maintain, and integrate with.

Resource names should generally be meaningful and predictable.

/api/customers

API versions can be introduced when breaking changes need to be released without immediately affecting existing clients.

/api/v2/customers

Pagination should be considered when an endpoint may return a large number of records.

GET /api/products?page=2&pageSize=20

Documentation should clearly explain endpoints, parameters, authentication requirements, responses, and possible errors.

Logging and monitoring can also help developers identify unexpected API behaviour and performance problems.

  • Use clear resource names.
  • Keep endpoint conventions consistent.
  • Document your API.
  • Consider versioning for breaking changes.
  • Use pagination for large collections.
  • Monitor API performance and failures.
